# 时间与浏览器时区

核对日期：2026-11-16。时间修复已经在 2026-11-09 的本地 Backend `ca9f3df`、Web `f94dd9a` 中完成；SDK 1.3.0 继续遵守同一时间协议。需要更新并重启 Backend、发布完整 Web/dist 才能用于部署环境。

## 自动转换规则

Web 每次通过公共 Axios 工具发送请求时读取浏览器 IANA 时区，并设置 `X-Time-Zone`，例如 `Asia/Shanghai` 或 `America/New_York`。设备时区改变后，下次请求使用新值；重新获取列表才会得到新的服务端展示值。

Backend 验证时区并仅保存在当前请求 context 中。普通 API 的 `timex.Time` 字段和相关 CSV 导出按请求时区显示；无头或无效值回退后端进程时区。有效值通过同名响应头返回，`Vary: X-Time-Zone` 区分缓存变体，CORS 已允许该请求头。

转换时复制输出对象，不改数据库记录、共享缓存或进程全局时区。后台定时任务、业务配额和身份校验仍使用各自既定规则。同一时刻 `2026-11-08T23:21:09Z` 在上海是 `2026-11-09 07:21:09`，在纽约是 `2026-11-08 18:21:09`；IANA 规则按对应日期处理夏令时。

## 第三方客户端怎样提交和读取

| 数据 | 接入规则 |
| --- | --- |
| Unix 秒／毫秒 | 表示实际瞬间，保持数值不变；先核对接口单位 |
| JWT 的 exp/iat/nbf、Webhook/HMAC 时间戳 | 按实际时钟校验，不加减时区偏移 |
| RFC3339 时间 | 保留 `Z` 或显式偏移；在展示层转换 |
| 无偏移的日期时间控件 | 按用户实际选择的时区解释，再转成明确的 RFC3339 提交 |
| 生日等纯日期 | 保留日期，不当成瞬间转换 |
| 普通字符串、自定义 JSON、原始 JSON | 不按字段名称猜测并改写 |

浏览器可用 `Intl.DateTimeFormat().resolvedOptions().timeZone` 取得 IANA 名称。自定义浏览器客户端可发送该值；非浏览器服务按需要显式指定。不要因一位用户传入时区而修改整个后端的 `TZ` 或服务器时钟。

`X-Time-Zone` 是显示偏好，**不会重解释任意请求正文**。Web 已在公告、优惠券、邀请码、GM 授权、玩家封禁和创建时间筛选的明确 API 边界转换无偏移控件值。SDK 接入方直接提交 RFC3339 即可；SDK 不会自动平移签名、JWT 或 Unix 值。原生 `time.Time` 的 RFC3339 响应由前端格式化，不经过 `timex.Time` 的展示转换。

## 原因、历史数据与排查

此前 `timex.Time` 输出时直接去掉来源时区，而 Scan 与 Parse 对无偏移字符串分别采用 UTC／本地时区，可能造成显示与解析错位。修复统一了默认显示与解析，并修正空时间、表单转换及 SQLite 按真实瞬间筛选。

没有批量给历史数据加减八小时，也没有结构迁移。旧 SQLite 无时区时间可能已经被驱动解释为 UTC；缺少原始时区证据时不能恢复其真实来源。

诊断时连续读取不缓存的 `GET /healthz`，检查 RFC3339 `time` 是否持续前进；再对照请求的 `X-Time-Zone`、响应和前端显示。构建时间、启动时间、历史记录或上一次页面快照都不能作为实时系统时钟。Linux／Docker 要查看实际后端进程的时区配置，而不只看宿主机终端。

用户最初报告的 `2026-11-08 11:21:09` 没有对应线上地址和实时响应证据，因此不能声称所有偏差都由时区造成，也不能把本地修复当作线上时钟已经校准。
